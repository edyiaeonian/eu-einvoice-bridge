1. 同一份輸入可同時產生 UBL 與 FA(3) 兩種 XML
2. FA(3) 產出通過官方 FA(3) XSD
3. 第 3 類落差(EN16931 有、FA(3) 無)產生警告但不中斷,且警告列出具體欄位
4. 第 4 類落差(FA(3) 必填、模型無)在輸出階段即失敗,不產生無效檔案
5. 多幣別案例可完整走通,展示 BT-6 與 FA(3) 匯率欄位的對應

## FA(3) 真正必填的結構

以解析程式從 XSD 萃取(已修正第一版誤把可選群組列為必填的錯誤):

```
Faktura
  Naglowek      KodFormularza、WariantFormularza、DataWytworzeniaFa(產生時間)
  Podmiot1      賣方:NIP、Nazwa、Adres(KodKraju、AdresL1)
  Podmiot2      買方:識別擇一(NIP | KodUE+NrVatUE | NrID | BrakID)、JST、GV
  Fa            KodWaluty、P_1(開立日)、P_2(發票號)、P_15(應收總額)、
                Adnotacje(一組法定聲明)、RodzajFaktury
```

值得注意:明細 `FaWiersz` 與買方名稱在 XSD 中皆為**可選**;反而 `JST`、`GV` 與整組 `Adnotacje` 是**必填**。

### 第 3 類:EN16931 有、FA(3) 無 → 捨棄並警告

已查證(步驟 1):

- 法人登記號 BT-30:FA(3) 的 `Stopka/Rejestry` 只有波蘭的 `KRS`、`REGON`,無法判定任意登記號屬於哪一種
- 免稅理由代碼 BT-121:FA(3) 沒有代碼欄位,要的是法源文字

原本列為候選的 BT-154 與 BT-113 查證後都**有**對應,改列第 1 類(見上表)。

**重要限制:第 3 類只能用在不影響金額的欄位**,見下一段。

### 第 4 類:FA(3) 必填、模型無 → 輸出前失敗

- 賣方沒有波蘭 NIP(`vat_scheme` 不是 `PL` 或沒有 `vat_id`)
- 缺少 `PolishExtras`,或其中缺少必填聲明
- 標準稅率不在波蘭稅率集合中(沒有 `P_12` 代碼、沒有小計格)
- 免稅明細沒有可對應到 `P_19A/B/C` 的法源

### 已查證:文件層級折讓與附加費 → 拒絕產出 FA(3)

FA(3) 的 `Fa` 底下沒有文件層級折讓元素。唯一看似相近的 `Rozliczenie/Obciazenia`、`Odliczenia`,官方說明是「加到 / 從 `P_15` 扣除的金額」,**只調整應付金額,不影響稅基**。而 EN16931 的文件層級折讓依 BR-S-08 會降低稅基與稅額。

若照第 3 類捨棄,FA(3) 的稅額會與 UBL 不一致,那份 FA(3) 在法律上是錯的;若放進 `Rozliczenie`,稅額不會跟著降,同樣不一致。所以**含文件層級折讓或附加費的發票,拒絕產出 FA(3)**,並在報告中說明原因。分攤到明細 `P_10` 是可能的延伸,但會改變每一行的金額與捨入,本階段不做。

這也修正了四類模型本身:**第 3 類「捨棄並警告」只對不影響金額的欄位安全。**已寫回規格第 7 節。

## 步驟

### 步驟 1:vendored FA(3) 資產與離線載入 ✅

1. 將 `schemat_FA(3)_v1-0E.xsd` 與 `bazowe/` 三個檔案原樣納入 `assets/fa3/`,附 MIT 授權與來源紀錄
2. 驗證模組加入 `Resolver`,把 `crd.gov.pl/.../DefinicjeTypy/` 對應到本機
3. 手寫一份最小的合法 FA(3) 當測試素材,確認能通過 XSD(因為沒有官方範例,這是第一個要打通的點)
4. 查清上面標示「待查證」與「待調查」的項目,把結論寫回規格第 7 節

**完成判準**:最小 FA(3) 離線通過 XSD;測試證明不加對應時載入失敗。

### 步驟 2:`PolishExtras` 模型

依上方第 2 類表格建立具名欄位,不用 dict。

### 步驟 3:FA(3) 輸出器

`Naglowek`、`Podmiot1/2`、`Fa` 表頭、`P_13`/`P_14` 分格、`FaWiersz` 與 `P_12` 代碼、`Adnotacje`(推導項 + `PolishExtras` 項)。黃金檔案測試。

### 步驟 4:落差回報

- 第 3 類:結構化警告(沿用 `ValidationIssue`,來源標為 `mapping`),列出被捨棄的欄位
- 第 4 類:結構化錯誤,**在產生任何 XML 之前**回報,一次列出全部

### 步驟 5:FA(3) 驗證與 CLI

- `validate` 模組新增 FA(3) 的 XSD 驗證
- CLI 支援輸出 FA(3),警告與錯誤沿用現有報告格式

### 步驟 6:多幣別

解除階段一對 BT-6 的拒絕:加入匯率,UBL 端補上 BT-111,FA(3) 端補上對應的匯率與以 PLN 表示的稅額欄位(待查證欄位名稱)。這是驗收標準 5,也是四類落差中「第 1 類與第 2 類同時出現在同一個欄位」的示範。

## 已決定的事(2026-09-21)

1. **波蘭法定聲明必須明確提供,不設預設值。**缺任何一項就是第 4 類失敗,一次列出全部缺漏。理由:預設值會產生「XSD 通過、KSeF 接受、但法律上錯誤」的發票。例如 `P_18A` 分割支付,某些商品超過 15,000 PLN 時依法必須為「是」,預設成「否」不會被任何驗證抓到。
2. **多幣別維持為階段二最後一步**,不另開階段。階段一已公開聲明 BT-6 留到階段二處理,README 的範例也是多幣別。
