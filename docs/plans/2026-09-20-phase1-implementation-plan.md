**對應規格**:`docs/specs/2026-09-20-ksef-en16931-bridge-design.md`
**階段目標**:從 JSON 輸入產生通過官方 XSD 與 Schematron 驗證的 EN16931 UBL 發票,並以 CLI 一次回報所有錯誤。全程離線。

**狀態:✅ 已完成(2026-09-21)** —— 六項驗收標準全數達成,117 個測試;外部審查修正後為 139 個。

## 執行紀錄:計畫與實際的差距

計畫依步驟執行,但實作過程中有幾處因**查證一手資料**而偏離原規格。這些偏離都已回寫進規格,此處記錄以免遺失脈絡:

| 步驟 | 發現 | 處理 |
|---|---|---|
| 0 | 官方 `BIS3_Invoice_negativ.XML` 針對 Peppol CIUS,不能當 EN16931 core 負面素材 | 負面測試改為自行竄改合法範例 |
| 1 | 驗證資產為 EUPL 1.2(copyleft) | 原樣 vendored 並附授權全文;本專案程式碼採 MIT,授權分離 |
| 2 | 免稅理由規則比規格多三類(G、K、O),且為雙向(S/Z 不得有) | 規格決策三改寫 |
| 2 | Pydantic 會把 float 靜默轉成 Decimal | 新增 `ExactDecimal`,在邊界拒絕 float |
| 3 | BR-CO-17 容差實為 ±1 貨幣單位,非 ±0.01 | 因彙總完全推導,模型不需容差檢查;僅用於測試斷言 |
| 3 | `O` 稅別要求稅率「不存在」而非為 0,且不可與他類混用 | 移出支援範圍 |
| 3 | BT-119 為百分比,模型存比例 | 稅率加 `le=1` 上限,防止填 23 算出 2300% |
| 4 | UBL-CR-601 要求明細層不應出現免稅理由(當時誤記為「禁止」,它其實是 warning 級規則) | 改為明確參數,不再以 `getattr` 猜測 |
| 5 | Schematron 對元素順序錯誤完全無感 | 以測試證明 XSD 層不冗餘 |
| 6 | Pydantic 把 JSON 語法錯誤也當驗證錯誤 | 偵測 `json_invalid`,改回傳離開碼 2 |

### 完成後的外部審查(2026-09-21)

階段一標記完成、repo 公開後,另一位審查者閱讀程式碼並附上一份契約測試。審查者無法執行程式,所以每一項都先在本機驗證才修。契約只有一句話:**模型接受的東西,序列化器必須忠實輸出,官方規則不得判為 fatal。**

| 發現 | 驗證結果 | 處理 |
|---|---|---|
| 所有 Schematron 失敗都當成錯誤 | 成立:979 條中 698 條是 warning。我第一次搜尋寫法錯誤而得到 0 筆,差點否定這個正確的指正 | 嚴重度依 `flag`,只有 fatal 讓發票無效 |
| 序列化器用 `f"{v:.2f}"`,把銀行家捨入帶回來 | 成立:`10.005` → `10.00`、單價 `0.125` → `0.12` | 貨幣輸入超過兩位小數就拒絕;序列化器不再捨入 |
| BT-6 會產出必然失敗的發票 | 成立:BR-53 要求 BT-111 | 階段一拒絕 BT-6 |
| 381 被接受但輸出 `<Invoice>` | 成立,而且更嚴重:直接違反 BR-CL-01 | 從列舉移除 |
| `Invoice` 可變,快取的合計會過時 | 成立:改預付金額後應付金額不變 | 全部模型 frozen、集合改 tuple |
| 明細淨額未與 數量 × 單價 比對 | 成立:官方核心規則沒有這條 | 模型層檢查,不一致回報不覆寫 |
| (審查未提)預付金額也是會被靜默捨入的輸入 | BR-DEC-16 | 同樣限制兩位小數 |
| (審查未提)`model_copy(update=...)` 繞過 frozen 且不驗證 | 以測試重現 | 覆寫 `model_copy`,有更新時重新驗證 |
| 每次驗證都重新編譯 900KB 的 XSLT | 實測 | 快取編譯結果:測試 4.25 秒 → 0.58 秒 |

**為什麼原本的測試沒抓到**:測試 fixture 一律讓單價等於淨額、都是兩位小數、幣別固定、不設 BT-6、而且從不產生只有警告的發票。這些 bug 全部落在 fixture 沒涵蓋的區域。

**環境問題**:macOS iCloud 同步使 venv 內檔案被設 `UF_HIDDEN`,而 Python 3.14 的 `site.py` 會跳過隱藏的 `.pth` 檔,導致 editable 安裝無聲失效。專案因此移至 `~/Projects`。測試以 `pythonpath = ["src"]` 隔離此問題。

## 驗收標準(來自規格第 3 節)

1. 從一份 JSON 輸入可產生 UBL 2.1 XML
2. 該 XML 通過 UBL 2.1 XSD 與 EN16931 core Schematron 兩層驗證
3. 模型可表達標準稅率、零稅率、免稅、逆向課稅四種稅別,且免稅與逆向課稅強制要求理由
4. 稅額彙總由明細推導,人工無法直接指定
5. 給定含多處錯誤的輸入,CLI 一次列出所有錯誤,每項含規則 ID、BT 編號、位置與可讀訊息
6. 全部測試不需網路即可通過

## 步驟

### 步驟 0:驗證 saxonche 可行性 ⚠️ 風險最高,必須最先做

**為什麼先做**:EN16931 Schematron 需要 XSLT 2.0,而 lxml 只支援 1.0。整個驗證層建立在 `saxonche` 能在 macOS ARM 上運作這個假設上。此假設若不成立,方案須重新設計(改用 Java/.NET 執行驗證,或改變架構)。**不可等到寫完模型才發現。**

**做法**:
1. 建立虛擬環境,`pip install saxonche`
2. 取得 EN16931 validation artefacts v1.3.16(含官方預編譯 `.xslt`)
3. 取得官方範例 UBL 發票 XML
4. 以 saxonche 執行該 xslt 對範例 XML 驗證

**完成判準**:能取得 SVRL 輸出(Schematron 的標準驗證報告格式),且內容可解析。

**若失敗**:停止,回報,重新評估技術選型。不要繞路硬幹。

### 步驟 1:專案骨架與驗證資產

**做法**:
1. `pyproject.toml`,src layout,pytest 設定
2. 依賴:`pydantic`、`lxml`、`saxonche`、`pytest`
3. 將驗證資產納入 `assets/`:
   - EN16931 預編譯 `.xslt`
   - UBL 2.1 XSD
   - 官方範例 XML(作測試素材)
4. 建立 `assets/README.md` 記錄每項資產的來源 URL、版本號、授權條款

**完成判準**:`pytest` 可執行(即使還沒有測試);資產齊全且來源有紀錄。

---

### 步驟 2:model — 基本結構

**做法**(TDD,測試先行):
1. 列舉:`VatCategory`、`InvoiceTypeCode`
2. `Address`、`Party`、`LineItem`、`AllowanceCharge`
3. 結構性驗證:必填、型別、列舉值
4. `E` / `AE` 稅別強制要求免稅理由

**完成判準**:四種稅別皆可表達;缺免稅理由的 `E` / `AE` 會被拒絕(對應驗收標準 3)。

---

### 步驟 3:model — 推導與捨入

**這是規格決策四與決策七的落實,是模型層最容易出錯的部分。**

**做法**:
1. 捨入輔助函式:`quantize(Decimal("0.01"), ROUND_HALF_UP)`
2. `vat_breakdown` 推導:
   - 依 `(category, rate)` 分組
   - 明細 `net_amount` 先 quantize 再加總得 `taxable_amount`
   - **以分組總額乘稅率**得 `tax_amount`(不是逐行算稅再加總)
   - 文件層級折讓/附加費依其稅別併入對應分組
   - 組內免稅理由不一致 → 資料錯誤
3. `totals` 推導:BT-106 / 107 / 108 / 109 / 110 / 112 / 113 / 115
4. 以 `@model_validator(mode="after")` 填入,並將兩者排除於輸入 schema

**必須包含的測試**:
- `.005` 邊界值 → 驗證確實是 `ROUND_HALF_UP`,不是 Python 預設的 `ROUND_HALF_EVEN`
- 「先分組加總再算稅」vs「先逐行算稅再加總」結果不同的案例
- 組內免稅理由衝突
- 嘗試直接指定 `vat_breakdown` → 應被拒絕(對應驗收標準 4)
- 含折讓的發票 → BT-109 ≠ BT-106

---

### 步驟 4:ubl 輸出器

**做法**:
1. 中立模型 → UBL 2.1 XML
2. 對照官方範例 XML 確認元素結構與命名空間
3. 注意 BT-153(`cac:Item/cbc:Name`)與 BT-154(`cbc:Description`)是不同元素

**完成判準**:產出可被 UBL 2.1 XSD 接受;黃金檔案測試建立(對應驗收標準 1)。

---

### 步驟 5:validate 模組

**做法**:
1. XSD 驗證(lxml)
2. Schematron 驗證(saxonche 執行預編譯 xslt)
3. **解析 SVRL 輸出**,轉成結構化錯誤物件:
   - 規則 ID(如 `BR-CO-10`)
   - BT 編號
   - 位置(XPath 或明細行號)
   - 可讀訊息
4. 兩層錯誤合併為同一種結構,呼叫端不需區分來源

**完成判準**:合法發票通過兩層;刻意做壞的發票能回報具體規則 ID(對應驗收標準 2)。

---

### 步驟 6:cli 與錯誤報告

**這是本專案唯一的產品介面,品質即門面。**

**做法**:
1. 讀 JSON → 建模型 → 產 UBL → 驗證 → 輸出報告
2. **一次列出所有錯誤**,不在第一個錯誤中斷
3. 錯誤來源分層顯示(模型層 / XSD / Schematron)
4. 每項含規則 ID、BT 編號、位置、可讀訊息

**完成判準**:給定含多處錯誤的輸入,一次列出全部(對應驗收標準 5)。

---

3. 狀態 badge

**完成判準**:CI 綠燈;README 可讓陌生人在五分鐘內跑起來(對應驗收標準 6)。

## 執行原則

- **TDD**:測試先行,尤其步驟 3 的捨入與推導邏輯
- **每步結束即 commit**,訊息說明「為何這樣做」而非「做了什麼」
- **規格標記「須查證」的項目,實作時打開一手資料對照**,不依記憶
- **遇到與規格不符的現實**(例如官方 XSD 的實際結構與預期不同),停下來更新規格,不要讓程式碼與規格默默分歧
