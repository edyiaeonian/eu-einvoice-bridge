# EU E-Invoice Bridge 設計規格

**日期**:2026-09-20
**狀態**:設計已確認,待撰寫實作計畫

---

## 1. 專案目的

建立一個可實際運作的電子發票處理管線,把一份中立的發票資料同時轉換成**歐盟語意標準 EN16931(UBL 2.1 語法)**與**波蘭國家格式 FA(3)**,通過官方規則驗證後,實際送入波蘭 KSeF 沙箱環境並取回官方收據(UPO)。

### 成功標準

1. 能從一份 JSON 輸入產生通過**官方 Schematron 驗證**的 EN16931 UBL 發票
2. 能產生 KSeF 接受的 FA(3) XML,並成功送入沙箱、取回 UPO
3. 兩種格式的**欄位落差被明確記錄與回報**,不靜默丟失資料
4. 沙箱不可用時,離線測試仍可全數通過
5. 程式碼結構清楚到可以在面試中逐層解釋

### 這個專案的定位

**作品集專案,不是商業產品。**目標是求職面試時的技術展示素材,不追求商業化。相關的市場評估結論見第 2 節。

## 2. 背景與前期研究結論

### 法規背景

歐盟 ViDA(VAT in the Digital Age)於 2025-03-11 正式通過、2025-04-14 生效,規定 **2030-07-01 起**歐盟境內跨境交易必須使用符合 EN16931 的結構化電子發票。各成員國國內強制時程不一:

| 國家 | 時程 |
|---|---|
| 波蘭 | 大企業 2026-02-01、全體 VAT 企業 2026-04-01、微型企業 2027-01-01 |
| 法國 | 2026-09-01 全體須能接收、大中型須開立;中小微開立 2027-09 |
| 德國 | 2025-01-01 起全體須能接收;開立 2027-01-01(營業額 >€80 萬)、2028-01-01 全體 |
| 匈牙利 | NAV RTIR 自 2018-07-01 起,2021 年起全面涵蓋 B2B/B2C |

### 為什麼選波蘭,而不是匈牙利

這是本專案第一個重要的技術決策,理由是**沙箱可及性**:

- **波蘭 KSeF ✅**:測試環境 `api-test.ksef.mf.gov.pl` 規定使用匿名資料,接受標準測試用假 NIP(如 `5555555555`),測試環境可在無真實授權下取得 token,自簽憑證自動產生。**不需要波蘭法人或稅號。**
- **匈牙利 NAV ❌**:註冊需要 Ügyfélkapu+(匈牙利政府電子閘道帳號)與匈牙利稅號,測試環境僅供已登記的納稅義務人使用。**無匈牙利法人實體則無法取得存取權。**

### 商業可行性結論(已評估,結論為不追求)

匈牙利市場自 2018 年起已飽和;波蘭主要強制浪潮於 2026-04 結束,已過去逾五個月;法國、德國市場雖仍有窗口,但需要在地法遵關係與通路。既有競爭者包含 Sovos、EDICOM、Pagero、Storecove(企業級)與 InsERT nexo、Comarch Optima、enova365(波蘭在地 ERP)。

**結論:作為創業題目時機與條件均不利,因此本專案定位為技術作品集。**

### Peppol 的角色

MVP 完全不需要 Peppol。自行取得 Access Point 認證並不實際(需 OpenPeppol 會員資格與 ISO 27001)。實務做法是接用現成 AP 供應商(約 €0.18–0.25/張,部分有免費方案)。**本專案不涉及 Peppol。**

## 3. 範圍

### 包含

- 中立發票資料模型(Pydantic)
- EN16931 UBL 2.1 輸出器
- KSeF FA(3) 輸出器
- 官方 Schematron 驗證器(EN16931 驗證規則)
- KSeF 沙箱客戶端:認證、送件、狀態輪詢、UPO 下載

- 發票的儲存與查詢資料庫(僅保留送件狀態的本地檔案)

## 4. 架構

### 資料流

```
                    ①  model          共用起點
                        │
            ┌───────────┴───────────┐
            ▼                       ▼
        ② ubl                   ④ fa3      把模型轉成 XML
            │                       │
            ▼                       ▼
        ③ validate              ⑤ ksef     拿 XML 去做事

                    ⑥  cli           使用者入口
```

### 模組職責

| 模組 | 負責 | 不負責 |
|---|---|---|
| `model` | 中立發票結構、型別、基本結構性驗證 | 不知道 XML,不知道任何國家格式 |
| `ubl` | 中立模型 → EN16931 UBL 2.1 XML | 不做驗證 |
| `fa3` | 中立模型 → KSeF FA(3) XML | 不負責送件 |
| `validate` | 執行官方 Schematron,回傳結構化錯誤清單 | 不修正錯誤 |
| `ksef` | 沙箱認證、送件、輪詢、下載 UPO | 不判斷發票內容正確性 |
| `cli` | 指令列入口,串接上述模組 | 不含任何商業邏輯 |

### 設計理由

**為何以中立模型為中心**:EN16931 與 FA(3) 並非一對一對應。若讓兩者直接互轉,程式碼會退化成大量特例判斷。兩者皆從同一中立模型出發後,落差被隔離在各自的輸出器內,清楚可見。

**為何每條路徑拆成兩個模組**:「轉格式」與「用這個格式去做事」的失敗原因完全不同——前者是輸入資料問題,後者是外部環境問題。拆開後可快速定位問題,且轉格式模組可完全離線測試。

**為何 CLI 不含邏輯**:未來加入 FastAPI 時可直接呼叫同一套核心,無需重寫。

## 5. 資料模型與欄位對應

### 模型結構

```python
class Address:
    street: str
    city: str
    postal_code: str
    country: str           # ISO 3166-1 alpha-2

class Party:
    name: str
    tax_id: str
    tax_scheme: str        # 稅號的發證國,例如 "PL"
    address: Address
    country: str

class Totals:
    net_total: Decimal
    vat_total: Decimal
    gross_total: Decimal

class LineItem:
    description: str
    quantity: Decimal
    unit_price: Decimal
    vat_rate: Decimal
    net_amount: Decimal
    vat_amount: Decimal

class Invoice:
    number: str
    issue_date: date
    currency: str
    seller: Party
    buyer: Party
    lines: list[LineItem]
    totals: Totals
    country_extras: dict   # 各國專屬欄位
```

### 決策一:模型只存語意,不存格式

稅率存 `Decimal("0.23")` 而非 `"23%"`;日期存 `date` 物件而非字串。同一個值在 UBL 與 FA(3) 的寫法可能不同,**格式化是輸出器的責任**。模型一旦混入特定格式,另一條路徑即被污染。

### 決策二:金額一律使用 `Decimal`,不使用 `float`

無例外。`float` 無法精確表示十進位小數,累加後產生誤差。稅額誤差即使僅一分錢也會導致退件。

### 決策三:三類欄位落差,三種處理方式

| 情況 | 處理 |
|---|---|
| 兩邊皆有 | 直接對應 |
| 波蘭專屬欄位 | 置於 `country_extras`,不混入主結構 |
| 歐盟有、波蘭無 | 輸出 FA(3) 時捨棄,**並回報警告** |

第三類**嚴禁靜默丟棄**。必須明確回報哪些欄位在送往波蘭時會遺失。

### 決策四:驗證分兩層且刻意不重複

- **模型層(Pydantic)**:結構性檢查(必填、型別)。快速、離線、錯誤訊息友善。
- **Schematron 層(官方)**:跨欄位語意規則。權威來源。

**不以 Pydantic 複製官方規則。**官方驗證規則會改版(現行 v1.3.16 發布於 2026-04-10),自行複製必然產生不同步。

### 刻意不做的抽象

欄位對應直接寫在各自的輸出器內,以清楚的函式命名表達,**不建立設定檔驅動的對應框架**。目前僅兩種格式,額外抽象層不划算。待實際新增第三、第四國時再重構。

### 待實作時確認的細節

FA(3) 的確切欄位名稱、結構與必填規則,需對照**官方 FA(3) XSD(schema version 1-0E)**確認,不得依記憶推測。同樣地,KSeF 2.0 的認證流程細節需對照其 OpenAPI 規格。

## 6. 錯誤處理

### 三類錯誤,處理方式不同

| 類型 | 例子 | 處理 |
|---|---|---|
| 資料錯誤 | 缺必填欄位、稅額計算錯誤 | **不重試**,直接回報 |
| 暫時性外部錯誤 | 網路逾時、沙箱 503 | **重試**,指數退避,有次數上限 |
| 永久性外部錯誤 | 認證失敗、憑證過期、官方拒絕 | **不重試** |

**資料錯誤必須一次回報全部**,不可遇到第一個錯誤即中斷。

### KSeF 非同步流程的處理

送件後不會立即得知結果,流程為:送出 → 取得參考編號 → 輪詢狀態 → 成功後下載 UPO。因此:

- **輪詢須有超時上限**,不得無限等待
- **中間狀態須持久化**:參考編號在送出前(或送出後立即)寫入本地檔案,程式中斷後仍可憑編號查詢
- **嚴禁自動重送**:未收到回應不等於未送達,重送可能造成重複發票。正確行為是「查詢」而非「重送」

### 安全

- token、憑證、金鑰**不得寫入程式碼,不得 commit**
- 使用環境變數搭配 `.env`,`.env` 於專案建立第一天即加入 `.gitignore`
- 本專案將公開於 GitHub,金鑰一旦進入 git 歷史即無法真正移除

## 7. 測試策略

| 層級 | 測試內容 | 需網路 | 速度 |
|---|---|---|---|
| 單元測試 | 模型驗證、兩個輸出器的 XML 產出 | 否 | 秒級 |
| 驗證測試 | 產出的 UBL 通過官方 Schematron | 否 | 中等 |
| 整合測試 | 完整送入 KSeF 沙箱流程 | 是 | 慢 |

**核心原則:沙箱不可用時,前兩層須能完整通過。**整合測試以 pytest marker 標記,預設不執行。

**黃金檔案測試**:保存已知正確的 FA(3) 與 UBL XML 作為基準,偵測非預期的輸出變動。

**測試素材**:使用官方提供的範例 XML,不自行編造。

## 8. 技術選型

| 項目 | 選擇 | 理由 |
|---|---|---|
| 語言 | Python | 使用者正在學習的語言,延續既有基礎 |
| 資料模型 | Pydantic | 型別驗證與錯誤訊息品質佳 |
| XML 處理 | lxml | 成熟穩定 |
| Schematron 執行 | **saxonche** | **關鍵**:EN16931 Schematron 需要 XSLT 2.0,而 lxml 僅支援 XSLT 1.0 |
| HTTP 客戶端 | httpx | 支援逾時與重試控制 |
| 測試 | pytest | 標準選擇,marker 機制符合分層測試需求 |

### 為何不改用 .NET/Java

該生態的 EN16931 函式庫較成熟(如 Lombiq/eInvoice-Validator),且原生支援 XSLT 2.0。但 `saxonche` 可透過 pip 安裝並解決 XSLT 2.0 問題,不足以構成放棄既有 Python 基礎的理由。

## 9. 已知限制

- 僅支援波蘭一國,無法宣稱為「多國方案」
- 僅連接沙箱,未經正式環境驗證
- 欄位對應涵蓋常見情境,非 FA(3) 完整規格
- 無使用者介面
